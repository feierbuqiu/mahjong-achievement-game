## 1. Overall assessment

The empty-position P result is well supported. The September forward and
reverse computations already established it, and V17 adds a kernel-proved
implication plus a complete native evaluation without importing old PASS
records. The publication is unusually explicit about claim classes:
UNKNOWN versus P, component PASS versus opening proof, AI review versus human
review. Its numbers are internally consistent everywhere I checked. Its
verifiers pass, and the saved-record graph in the public ZIP is sound.

The problems sit where a trust paper can least afford them: in **what the
production run actually checked natively** and **what the evidence actually
contains**.

- **Cross-layer target identity.** In the production configuration, the
  native check compares a loaded object with itself. The 54,548
  bookkeeping "references" are equal by construction. The cross-layer
  obligation is actually discharged by input custody, which the documents
  understate. The AI review describes the mechanism incorrectly (M1).
- **Bucket exact cover.** The native exact-cover Boolean is computed but
  never gated by the production controller. Its 3,686 bucket-close records
  are not in the evidence asset. The "deleted final row" control exercises a
  gate that production does not use (M2).
- **Overstated wording.** The repeated phrase "the same check functions …
  accepted the complete actual input" is stronger than what ran (M3).
- **Other major defects:**
  - a personal workstation path published since 15 September (M4);
  - evidence-asset omissions that make the custody handover unauditable (M5);
  - unpublished code inside the stated trust boundary (M6);
  - a mislabelled "historical" status block (M7);
  - a thin literature base for a paper about trust in computation (M8).

None of this changes the P result. It does change what the repository may
truthfully say about how the V17 premises were established.

## 3. Major findings

### M1. Cross-layer target identity: the native check is vacuous in production, and the bookkeeping comparison is tautological

**What the code does.**

- `research/2026-10-19-v17/source/V17ComputeMain.lean:178–183`: when the
  target roots equal the source roots, the "canonical" next-layer bucket is
  `pure loaded`. That is the same in-memory object just loaded for the
  target role. No second read happens.
- `research/2026-10-19-v17/source/ops/plan_run.py:7–12, 62–63` allows exactly
  ten root fields, with no target roots. `V17ComputeMain.lean:53–65`
  (`optField … "target_index_root" index`) defaults the target roots to the
  source roots. Production therefore always takes the `pure loaded` branch.
- `V17ComputeMain.lean:193`: `checkTargetSources bucket.work.next next`
  compares a bank built from `loaded`'s fields with `loaded` itself. Apart
  from the honour-code substitution, which lines 184–189 check separately,
  this is true by construction. It cannot detect anything.
- Bookkeeping: `ops/controller.py:322–323` writes both `source_identity` and
  `target_identities`. Both come from `finalize.source_identity(manifest,
  plan, cell)`, defined at `ops/finalize.py:47–48` as `seven_fields(cell,
  manifest['inputs_before'], plan['common_identity_fields'])`. The same
  function, with the same inputs, produces both sides. The equality checked
  at `finalize.py:74–77`, `research/2026-10-19-v17/verify.py:118–122` and
  `papers/trust-verification/native_record_audit.py:97` is guaranteed by
  construction. It shows only that the bookkeeping is deterministic, not
  that the bytes the native processes read were the same.
- The `target_identity_mismatch` control (`ops/native_controls.py:137–144`)
  points `target_data_root` at a shadow directory. That is a configuration
  production never uses. The control proves the check works when the roots
  differ, not that production would detect a substitution.

**What actually discharges the obligation.** The target-role load in bucket
`(n,h)`'s session and the source-role load when bucket `(n+1,h′)` is opened
read the same path. Both reads happen under Windows deny-write custody, and
the before and after full-input hash maps are equal. This is a sound
argument **under the custody assumption**, but it is an assumption, not a
check.

**Inaccurate statements to correct.**

- `papers/trust-verification/native_evidence.md:126`: "The in-process target
  identity check reloads the same file roots … This does not make the check
  itself vacuous—the changed-target control rejects". In production there is
  no reload, and the check is vacuous. The control uses a different
  configuration.
- `research/2026-10-19-v17/review/INDEPENDENT_REVIEW.md:135`: "It compares the
  loaded target with a second load of the same file". There is no second load.
- `research/2026-10-19-v17/README.md:62`: "native byte checks plus … seven-field
  comparison by bookkeeping". Neither adds detection power in production.
- `research/2026-10-19-v17/README.md:72–75`: "depends on immutable inputs and
  their hash binding **as well as** the native check". It should say
  **rather than**.
- `research/2026-10-19-v17/README.md:87` ("54,548 cross-layer target references,
  zero identity mismatches") and `papers/trust-verification/manuscript.md:181`
  ("reconciled 54,548 cross-layer target references") present a tautology as
  evidence.

**Required fix.**

1. Rewrite these passages. Suggested wording is in Section 9.
2. State plainly that cross-layer identity is an input-custody assumption,
   discharged by fixed paths, deny-write locks and equal before/after maps.
3. Add an erratum to the AI review (see S6).
4. For any future run, make the check meaningful:
   - have the native process emit a content hash of the bytes it actually
     read for every source and target bucket, and compare those across
     sessions; or
   - read targets from an independently hashed copy.

### M2. Bucket exact cover: computed natively, never gated, records not published

**What the code does.**

- `V17ComputeMain.lean:325–331`: on `close`, the native process computes
  `ScanFinalV17.checkRanges` and **emits** `exactCoverage` as a Boolean in a
  `BUCKET_CLOSED` event. It does not throw.
- `ops/controller.py:338–340`: the production controller checks only `ranges`
  and `checked_rows`. It never requires `exactCoverage is True`.
  `ops/fused_worker.py:158–160` also returns `BUCKET_CLOSED` unchecked.
- `controller.py:340` writes `buckets/<bid>.closed.json` for every bucket.
  The published ZIP contains 3,686 `*.ready.json` records and **zero**
  `*.closed.json` (I enumerated all 38,330 members). `assets.json` does not
  mention the exclusion. So the evidence that the native cover Boolean was
  true for each bucket is not public.
- The `deleted_last_row` control (`ops/native_controls.py:123, 216–219, 248–251`)
  counts as a rejection precisely because `exactCoverage` is false. That is
  the very Boolean production ignores. In production, a missing final row
  would be caught by Python: the controller's cursor loop and
  `finalize.verify_entries`, re-checked by `verify.py --archive` and
  `native_record_audit.py:67, 96`. That Python check is sound, but it is not
  the native Lean function.

**Inaccurate statements to correct.**

- `INDEPENDENT_REVIEW.md:127`: "In production (`serve`) mode, any rejection
  raises an error and ends the process." This is false for the exact-cover
  check.
- `research/2026-10-19-v17/README.md:105–107` and
  `papers/trust-verification/manuscript.md:189` list the deleted-final-row
  control without saying that it tests a gate production does not consult.
- `evidence/final.json` (`six_acceptance_families_complete`), the CHANGELOG
  ("all six acceptance families") and the README imply that all six families
  were evaluated natively. The cover conjunct of the frames family was
  established by Python bookkeeping. To its credit,
  `research/2026-10-19-v17/README.md:61` does say "plus external exact-cover
  bookkeeping".

**Required fix.**

1. If the 3,686 close records exist, publish them as a supplementary asset.
   The existing immutable release cannot change, so this means a new
   asset/release, which is your decision. Then extend `verify.py --archive`
   to require `exactCoverage is True` for every nonempty bucket. If the
   records were not retained, say so.
2. Correct the wording about controls and "fails closed".
3. For future runs, make the controller refuse a bucket unless the native
   Boolean is true.

### M3. "The same check functions … accepted the complete actual input" overstates what ran

- **Locations:** `README.md:11–13`, `docs/CLAIMS.md:12` and `docs/CLAIMS.md:29–33`
  (the "Suggested wording" block, which invites verbatim reuse), plus
  similar phrasing in the paper.
- **What the theorem assumes.** `from_finite_input` assumes whole-input
  Booleans: `checkWhole`, `targetChecks`, `checkMetadata` and so on, over one
  `Candidate` table.
- **What ran instead.** Production evaluated *decomposed adapter functions*
  (`V17NativeWorker.checkBase`, `checkEdges`, `openBucket`,
  `scanOwnedFragment`, `finishFrame`, …), one bucket session at a time.
  Python assembled the results.
- **The typed route was not used.** The only typed whole-input route,
  `finishWhole`, was not used. Its own docstring
  (`V17NativeWorker.lean:236–239`) says "The IO loader must supply one
  Candidate/Trace over the same Session, not independent reports. Keeping
  only report strings cannot call this function."
- **Consequence.** Given M1 and M2, at least two premises were not evaluated
  as native Booleans over a single input instance: `targetChecks`, and the
  `checkCover` half of `checkBucket`.

**Required fix.** Replace the phrase everywhere with a precise statement
(Section 9). For example: "Natively compiled component checks accepted every
frame, bucket and global premise; their assembly into the theorem's
whole-input premises, exact cover and cross-layer identity rest on external
bookkeeping and input custody." `docs/CLAIMS.md:34`'s trust-boundary list is
good and should stay.

### M4. Personal workstation path published; privacy scanners do not detect it

- `research/2026-09-15/evidence/operational-acceptance.json` (lines 23, 28,
  29, 32, 40, 42, 50, 52) contains
  `<research-root>\\…`.
  That exposes a Windows username and an institutional OneDrive folder.
- It has been public since 15 September (`2f92000`) and is contained in the
  immutable `v1.0.0` tag.
- AGENTS.md: "Never publish … personal workstation paths."
- **Why the scanners miss it.** `tools/verify_repository.py:123` uses
  `[A-Za-z]:[\\/](?:Users|home)[\\/]`, which expects one separator. JSON
  stores each backslash as two characters (`C:\\Users\\`), so the regex never
  matches. I confirmed it returns no match on this file. The same flaw is in
  `research/2026-10-18/verify.py:13` and
  `research/2026-10-18-kernel/verify.py:12`.

**Required fix.**

1. Publish a redacted copy, replacing the prefix with a placeholder (the
   repository already uses `<user-home>` elsewhere).
2. Record the transformation in `research/2026-09-15/provenance.json`. Keep
   the original hash in `evidence/acceptance.json:2985`, add the new
   published hash, and regenerate `CHECKSUMS.sha256:1718`.
3. Make the regex tolerant of escaped separators, for example
   `[A-Za-z]:(?:\\\\|\\|/)+(?:Users|home)(?:\\\\|\\|/)`, and also scan
   JSON-decoded strings.
4. Decide whether the copies in history and in `v1.0.0` matter to you.
   Policy forbids rewriting `main`, so that decision is yours.

### M8. The trust paper's literature base is too thin for its subject

`papers/trust-verification/manuscript.md:389–411` has 11 references:

- three self-citations;
- two single source files from the Lean repository;
- one documentation page;
- one Bilibili post;
- four scholarly works: Boutin 1997, de Moura & Ullrich 2021,
  Necula 1997 and Pollack 1997.

Each is cited once. The statement "Established verification methods are
attributed to their sources" (line 379) is not borne out.

A paper whose contribution is calibrating trust in a very large
computer-assisted result should engage at least with:

- **Large computations with checkable certificates:** the Four Colour
  Theorem in Coq, the Flyspeck/Kepler proof, and SAT-certificate results
  such as Boolean Pythagorean triples with DRAT/LRAT proofs and verified
  checkers.
- **The de Bruijn criterion and the meaning of "machine-checked":**
  Barendregt & Wiedijk.
- **Certifying algorithms:** McConnell, Mehlhorn, Näher & Schweitzer, which
  is exactly the "untrusted GPU proposer plus checked certificate" pattern
  used here.
- **Independent Lean kernels and checkers:** for example Carneiro's
  Lean4Lean (arXiv:2403.14064). The paper's own recommendation 5
  (`manuscript.md:373`) calls for independent checkers.
- **Game solving and retrograde analysis:** Thompson 1986; van den Herik,
  Uiterwijk & van Rijswijck 2002; Schaeffer et al. 2007 ("Checkers is
  solved").

Appendix B of this report lists candidates. **Verify every entry against the
publisher before adding it**; I could not resolve DOIs from this sandbox.
